# 交付说明（给你晚上看）

## 一句话
做了一个叫 **seal** 的小工具：**给 AI 干的活盖章**——一条命令生成可核验的交付凭证，甲方能验、下一个 AI 能接手。零依赖、离线、不上传。

## 为什么是这个（不是又一个 agent 插件）
我查了 2026-11-15 的 GitHub 热度：`agent-skills` 话题 44,315 个仓库、MCP 榜单前 50，**全都在给 agent 加能力**——能开浏览器、能记忆、能画图、能查数据库。没人做"加了这么多能力之后，怎么证明它干的活是真的"。

学术侧只有 PROV-AGENT（arxiv 2508.02866）这类溯源模型，没有工程实现。

所以定位是一句反话：**别的工具帮 agent 多做一点，seal 让做的这点能被验收。**

## 能干什么（四条命令）
| 命令 | 干什么 |
|---|---|
| `node bin/seal.js` | 盖章：扫近 30 分钟改过的文件 + 命令记录 → `receipt.json` + 一页 A4 的 `receipt.html` |
| `... verify` | 验真：重算链哈希、逐文件哈希，**还会真重跑**标了 `recheck` 的命令并比对输出指纹 |
| `... resume` | 接管：把凭证翻成人话简报（改了哪些文件 / 验过什么 / 下一步），换个会话接着干 |
| `... show` | 打开那张 A4 凭证 |

## 我亲手验出来的数（不是员工自报）
- 自测 **41/41** 通过，6.0 秒。
- 盖章 **0.20 秒**，产物 792 B JSON + 4.4 KB 网页。
- 改文件一个字节 → `不通过 2/3：a.txt 哈希不一致（凭证 c4d9a0aa… / 现状 00bb9cdb…）`，退出码 1。
- 改凭证里一个字 → `链哈希不一致（凭证 097fbfcf… / 现算 1519d065…），凭证正文被改过`，退出码 1。
- 两次盖章串链：第二份 `prev` = 第一份 `hash`（`c90cfb97…`），verify 通过。
- recheck：把输出记成 `42` 而非真实的 `42\n`，verify 立刻报「输出指纹对不上」——**它比的是真输出，不是自述**。
- 零联网：4 个 JS 只 require `crypto/fs/os/path/child_process`，`dependencies: {}`。
- 演示：`demo\run-demo.cmd` 双击跑四步，末行「这就是它存在的理由：文件被人动了一个字节，凭证当场指出来，不用翻聊天记录。」

## 谁会要它
- 把活外包给 AI 的人（自由职业、外包团队）：交付时附一张凭证，甲方能自己验。
- 用 agent 写代码的团队：PR 里贴凭证，reviewer 先看结论再看 diff。
- 多 agent / 多会话接力：`resume` 就是给"下一个 AI"看的交接单。

## 风险与对策
- **被当成"又一个日志工具"**：README 与落地页都写了"日志 ≠ 凭证"的三条对照，用真失败案例演示。
- **价值被质疑（自己能改凭证吗）**：链哈希 + `verify` 重算，我在验收里专门做了"改一个字就验不过"的证据。
- **名字撞车**：`seal` 同名项目不少，发布时若撞得厉害，改 `package.json` 的 name 与 README 首行即可，代码不用动。
